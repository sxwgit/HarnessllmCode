# 严格开发导向改造指导文档

## 1. 目标

本次改造的最终目标不是“让测试全绿”，而是把现有测试体系升级为一套可严格指导开发的可执行规范。

满足以下条件时，才认为测试体系具备严格指导开发能力：

1. 框架中的每条 P0/P1 规则都能被机器直接判定通过或失败。
2. 核心约束由运行时 guard 强制执行，而不是仅靠事后测试发现。
3. 测试主要验证运行时行为，不再依赖源码字符串、注释、prompt 文案是否存在。
4. 任意“伪装成通过”的实现都能被反作弊测试识别并失败。
5. 即使当前实现全部失败，开发者仍然可以只靠测试逐步把实现推到正确状态。

## 2. 改造原则

### 2.1 从“审查清单”升级为“可执行法律”

现有文档覆盖面已经较好，但仍有一部分规则停留在评审语言，例如：

- “明显小于”
- “合理”
- “完整”
- “可运行”

这类描述不能直接指导开发，必须改写为以下三类可执行约束：

1. 结构约束：文件、字段、状态、分支、目录必须存在且符合固定格式。
2. 行为约束：在给定输入下，系统必须进入指定状态或拒绝指定行为。
3. 结果约束：评分、阈值、交付物、日志、Git 轨迹必须满足固定判定规则。

### 2.2 核心规则必须同时具备 4 层闭环

每条关键规则都必须具备：

1. 规范条款：来自 `docs/framework.md` 的原始约束。
2. 运行时 guard：代码中主动阻止违规路径。
3. 行为测试：验证 guard 在真实执行路径上生效。
4. 审计证据：Git、日志、状态、产物中能看到结果。

只存在其中一层，不算严格。

### 2.3 优先级

优先改造 P0 铁则和会直接放松约束的路径，顺序如下：

1. 受保护分支和 Git 时间线
2. 验收硬阈值
3. 规划阶段和最终验收的硬失败门禁
4. 预验收交付物门禁
5. 上下文轻量化和结构化交接
6. 人工介入、隔离、异常升级链路

## 3. 严格测试的判定标准

一条测试只有同时满足以下条件，才算“可指导开发”：

1. 它验证的是运行结果，而不是源码里是否出现某段文字。
2. 它可以明确指出失败原因，而不是仅说“没包含某关键词”。
3. 它能阻止常见投机实现。
4. 它和框架条款之间存在 1:1 或 1:n 的稳定映射。

反例：

1. 读取源码后断言 `toContain('任何维度 < 6分')`
2. 读取 prompt 后断言 `toContain('严禁Stub代码')`
3. 读取 orchestrator 源码后断言 `indexOf('PRE_EVALUATION') < indexOf('EVALUATION')`

正例：

1. 传入“报告写着通过，但维度分数低于 6”的评审报告，系统必须判失败。
2. 规划产物连续 3 次 Schema 校验失败，流程必须中断，不能继续打 Tag。
3. 预验收缺少合同交付物时，系统必须阻止进入正式验收。
4. 在 `main/dev` 上调用普通提交时，系统必须拒绝；只有显式批准路径才能提交。

## 4. 当前仓库的主要差距

### 4.1 测试层差距

1. 大量关键测试仍以源码字符串匹配为主，无法验证真实行为。
2. 一些测试目标很严格，但执行断言被弱化成“文件存在”“章节存在”“prompt 有文案”。
3. 反作弊测试不足，容易被“写一段描述文本”绕过。

### 4.2 实现层差距

1. 部分 guard 只是“提醒”，没有变成阻断逻辑。
2. 一些阶段在校验失败后仍继续向后推进。
3. 一些最终判断依赖自由文本结论，而不是结构化规则。

## 5. 本轮开发范围

本轮改造先完成第一批 P0 严格化，要求“代码 guard + 行为测试”成对落地：

### P0-01 受保护分支严格化

目标：

1. 默认禁止对 `main/dev` 执行普通提交。
2. 只有显式批准的框架路径才能在受保护分支提交。
3. 测试必须验证真实 `GitManager` / `Harness` 运行路径，而不是只看源码。

### P0-02 验收硬阈值严格化

目标：

1. `验收通过` 文案不能覆盖 6/7 分硬阈值。
2. 缺少维度分数、缺少总分、缺少明确结论时，一律按失败处理。
3. 测试必须覆盖“文案写通过但分数不达标”的反作弊场景。

### P0-03 规划阶段硬失败

目标：

1. 规划文档连续校验失败后必须中止流程。
2. 不允许继续提交、合并、打 Tag。
3. 测试必须验证失败后流程真正中断。

### P0-04 最终验收硬失败

目标：

1. 最终验收报告缺失或不完整时，流程必须失败。
2. 不允许使用兜底模板把“未完成验收”伪装成“已通过验收”。
3. 测试必须验证缺报告时会抛错，而不是自动补一份再继续。

### P0-05 预验收交付物门禁

目标：

1. 合同列出的核心交付物缺失时，预验收必须失败。
2. 不能只检查“有源码文件”，必须检查核心交付物是否齐全。
3. 测试必须覆盖“合同存在、源码存在，但关键交付物缺失”的场景。

## 6. 编写和修改测试的规则

1. 优先新增行为测试，再修改实现。
2. 单条测试只验证一个明确约束。
3. 每条 P0 测试必须至少包含一个反作弊输入。
4. 测试失败信息必须能够直接指导修复。
5. 能调用真实模块就不要退化成字符串检查。

## 7. 规范-测试-实现追踪模板

后续每个关键约束都应补齐如下追踪项：

| 条款ID | 规范来源 | 运行时 guard | 行为测试 | 证据 |
|--------|----------|--------------|----------|------|
| P0-01 | 受保护分支规则 | `GitManager.commit` | `GIT_*` 行为测试 | Git 历史 / 分支 |
| P0-02 | 评估硬阈值 | `Harness.checkEvaluationPassed` | `IRON_*` 行为测试 | review report |
| P0-03 | 规划阶段格式门禁 | `Harness.planning` | `ARCH_*` 行为测试 | 规划文档 / Tag |
| P0-04 | 最终验收门禁 | `Harness.finalAcceptance` | `DELIV_*` 行为测试 | final acceptance report |
| P0-05 | 预验收交付物门禁 | `PreEvaluator.runPreEvaluation` | `ARCH_*` 行为测试 | sprint contract / files |

## 8. 完成定义

本轮开发完成的标志不是“仓库里多了文档”，而是：

1. 第一批 P0 规则已经变成运行时硬约束。
2. 对应测试已经从静态检查升级为行为测试。
3. 旧的宽松兜底路径已被移除或收紧。
4. 测试失败时能准确暴露实现缺口，而不是暴露文案差异。

## 9. 当前最终目标差距矩阵

下面这张表不是看“测试数量”，而是看距离“可严格指导开发”还差多少闭环能力。

| 能力域 | 最终目标 | 当前状态 | 还差什么 |
|--------|----------|----------|----------|
| Git治理 | 受保护分支、回退、里程碑、审计全部有运行时硬保护 | 已完成基础闭环 | 还需补强批量回退整理与更细粒度发布前 Git 证据 |
| 验收判定 | 评分、维度、一票否决、结论全部结构化判定 | 已完成基础闭环 | 还需把问题清单质量也纳入硬判定 |
| 规划与验收门禁 | 规划失败、预验收失败、最终验收失败、发布证据不足都会直接阻断 | 已完成基础闭环 | 还需补阶段前后置条件 guard，避免“在错误前提下进入阶段” |
| 状态机 | 所有核心状态都只能按规范流转 | 已完成基础闭环 | 还需把阶段进入条件和状态流转条件完全对齐 |
| 结构化产物 | 关键产物不仅有章节，而且语义可用于程序判断 | 部分完成 | 还需补 requirement、review issue、summary 等更强语义约束 |
| 开发指导性 | 测试失败能直接告诉开发者应该补哪类实现 | 部分完成 | 还需继续减少字符串测试，增加行为级和反作弊测试 |
| 断点续跑/恢复 | 恢复后只重跑必要阶段，不跳过未完成工作 | 部分完成 | 还需补更多恢复场景测试与阶段级 guard |
| 结构化交接 | 规划、协商、评审、发布各阶段都通过可校验结构传递 | 部分完成 | 还需进一步从 Markdown 约束推进到 schema 驱动读写 |

## 10. 当前完成度判断

从“最终目标”角度看，当前不是 100% 完成，更接近下面这个状态：

1. 第一层：核心硬门禁已经基本成形。
2. 第二层：测试已经能卡住一批真实放松约束的实现。
3. 第三层：还没有完全变成“开发只跟着测试走就一定走到正确实现”的程度。

当前剩余差距主要集中在三类：

1. 阶段前置/后置条件还不够显式，部分阶段更多依赖流程顺序而不是显式 readiness guard。
2. 结构化产物虽然已经过了“有章节”这一关，但还没有全部收紧到“内容足以指导开发和修复”的强语义约束。
3. 一部分测试仍然偏向契约存在性检查，而不是完整运行路径上的行为约束。

## 11. 分批路线

### 已完成批次

1. 第一批：受保护分支、评估硬阈值、规划失败中断、最终验收失败中断、预验收交付物门禁。
2. 第二批：轻量上下文真实生效、发布前证据门禁。
3. 第三批：协商/架构反馈结构化约束、异常升级链路可观察化。
4. 第四批：合并后验证从 LLM 文本判定改为确定性命令执行、最终验收结论硬门禁。
5. 第五批：状态机非法跳转硬拒绝、关键产物语义校验初步落地。

### 待完成批次

#### 第六批：阶段 readiness + 需求/评审语义增强

目标：

1. `standard_requirement.md` 不再只是“生成了就算完成”，而是要满足最小可开发语义。
2. `review_report_xx.md` 的问题清单必须具备可执行修复信息，不能只有空泛描述。
3. `FINAL_ACCEPTANCE` 必须验证“所有 Sprint 已完成”，不能只因为流程走到了这里就允许进入。

#### 第七批：恢复链路与阶段级后置条件

目标：

1. 断点恢复必须精确回到未完成阶段，不能因为状态归一化过粗而跳过剩余工作。
2. 每个关键阶段完成后，都要有对应的 post-condition 校验，而不是只保存 checkpoint。

#### 第八批：结构化交接再收紧

目标：

1. 合同、评审、发布证据进一步从 Markdown 解析推进到更明确的 schema 驱动读写。
2. 让“生成了文档”和“生成了可执行规范对象”之间的差距继续缩小。

## 12. 本轮开发的完工标准

第六批完成时，至少要满足：

1. 无法通过不完整的标准化需求进入后续规划。
2. 无法通过缺少文件/行号/根因/修复建议的问题清单让评审报告过关。
3. 无法在仍有未完成 Sprint 的情况下进入最终验收。
4. 上述三类规则都要由运行时 guard 和行为测试共同覆盖。
