# 严格化改造进展与后续路线图

更新时间：2026-04-08

## 1. 文档目的

这份文档用于回答两个问题：

1. 目前为了把测试体系升级为“可严格指导开发的可执行规范”，已经做了哪些事情。
2. 距离最终目标还差哪些能力，后续应该按什么批次继续推进。

本文件强调的是“规范闭环能力”，不是单纯的“测试数量”或“测试是否全绿”。

## 2. 最终目标

最终目标不是“当前实现都通过测试”，而是达到下面这个状态：

1. 开发者可以直接把测试当作可执行规范来实现代码。
2. 即使当前实现全部失败，测试也能准确指出缺了哪条规则、哪类 guard、哪种产物语义。
3. 关键约束由运行时硬保护执行，而不是依赖人工审查或 prompt 文案提醒。
4. 关键流程无法靠“写一段看起来正确的话”绕过。
5. 规范、实现、测试、审计证据之间形成稳定闭环。

换句话说，最终要得到的是一套“开发必须服从的可执行法律”，而不是“覆盖面很大的审查清单”。

## 3. 进展总览

截至 2026-04-08，严格化改造已完成 6 批。

当前总体判断：

1. 核心硬门禁已经基本成形。
2. 一批关键规则已经从“文档要求”变成“代码 guard + 行为测试”双闭环。
3. 当前测试体系已经明显比初始状态更能指导开发，但还没有完全达到“只跟着测试走，就一定能走到最终正确实现”的程度。

当前测试回归结果：

1. `harness_meta` 全量测试通过。
2. 当前结果为 `165/165` 通过。

## 4. 已完成事项

### 4.1 第一批：P0 核心硬门禁

这一批的目标是先收紧最容易被放松、也最影响规范可靠性的几条铁则。

已完成内容：

1. 收紧受保护分支提交规则。
   现在默认禁止在 `main/dev` 上做普通提交，只有显式批准路径才能提交。

2. 收紧评估硬阈值。
   `review_report` 不能再靠“文本写了通过”绕过 6/7 分硬阈值；缺维度、缺均分、缺明确结论时默认失败。

3. 收紧规划阶段失败处理。
   规划文档连续校验失败后，流程会直接中断，不允许继续提交、合并、打 Tag。

4. 收紧最终验收失败处理。
   最终验收报告缺失或不完整时会直接失败，不再自动补一份“看起来成功”的报告继续流程。

5. 收紧预验收交付物门禁。
   合同列出的核心交付物缺失时，预验收会直接失败。

这一批解决的核心问题：

1. “写了规则，但实现里默认放开”。
2. “校验失败了，但流程继续推进”。
3. “报告里写通过，就能压过真实阈值”。

### 4.2 第二批：轻量上下文与发布证据门禁

这一批的目标是收紧上下文传递和发布前证据完整性。

已完成内容：

1. 让轻量上下文真实进入生产调用路径。
   之前 `buildLightweightContext()` 虽然存在，但真实调用未使用；现在 `Planner/Generator/Evaluator` 都会在实际调用时带上轻量上下文。

2. 增加发布前证据门禁。
   `RELEASE` 前必须校验最终验收报告、`README`、项目总结报告，不完整则阻断发布。

这一批解决的核心问题：

1. “基类里有约束，但真实运行路径没用”。
2. “发布前只看有没有文件，不看是不是完整证据”。

### 4.3 第三批：结构化协商/反馈与异常升级链路

这一批的目标是让协商结果、架构反馈、异常升级不再停留在宽松文本层。

已完成内容：

1. 收紧 Sprint 合同协商 payload。
   自相矛盾的协商结果会被直接打回，例如：
   `agreed: true` 却同时附带未解决 concerns；
   `agreed: false` 却不给出问题列表。

2. 收紧架构反馈提取规则。
   只有明确的架构反馈章节、结构化问题项和清晰决策标记，才会被识别为正式反馈。

3. 异常升级变成可观察行为。
   异常处理现在会显式返回 `upgraded` 标记，升级信息也会被写入 metrics。

这一批解决的核心问题：

1. “文本看起来像协商完成，但结构上不一致”。
2. “只要提到架构就算架构反馈”。
3. “异常升级是隐式发生的，系统无法审计”。

### 4.4 第四批：后验收确定性校验

这一批的目标是把后验收阶段残留的自由文本判断继续改成确定性判断。

已完成内容：

1. 把 `runPostMergeVerification()` 改为确定性命令执行。
   现在会按项目实际情况执行 `tsc`、`node --check`、`npm run build`、`npm run test`、`python -m py_compile`、`go build` 等命令，并依据真实退出码判断通过与否。

2. 收紧最终验收结论判断。
   最终验收报告不仅要完整，还必须明确写出通过结论；如果写的是不通过或缺失明确结论，则直接失败。

这一批解决的核心问题：

1. “由 LLM 文本解释工具结果，而不是根据命令真实结果判定”。
2. “报告结构完整，但结论其实是不通过，也能混进发布链路”。

### 4.5 第五批：状态机 guard 与关键产物语义校验

这一批的目标是让状态机和关键产物不再只靠章节存在性或顺序约定。

已完成内容：

1. 增加状态机跳转白名单。
   `meta/project` 两套状态现在都只能按显式白名单流转，非法跳转直接抛错。

2. 收紧 `product_spec.md` 语义校验。
   不再只检查章节存在，还要求至少有核心功能和用户故事。

3. 收紧 `sprint_plan.md` 语义校验。
   需要有 Sprint 标识和里程碑信息。

4. 收紧 `review_report_xx.md` 语义校验。
   需要显式 Sprint ID、5 个评分维度、有效均分、明确结果。

5. 让真实文件名也能命中校验器。
   例如 `review_report_sprint-01.md`、`sprint_contract_sprint-01.md` 现在也能正确命中 schema 与 semantic 双重校验。

这一批解决的核心问题：

1. “状态机可以被测试或实现直接跳过关键阶段”。
2. “文档有章节壳子，但对开发没有约束意义”。
3. “校验器只在理想文件名上严格，真实文件名反而漏掉”。

### 4.6 第六批：阶段 readiness 与需求/评审语义增强

这一批的目标是把“阶段进入条件”和“开发指导性最关键的文档语义”继续收紧。

已完成内容：

1. 收紧 `standard_requirement.md` 语义。
   现在要求至少具备：
   项目名、足够具体的项目概述、核心功能、技术栈约束、不做范围。
   不再允许“生成了一份标准化需求文档”就直接进入后续规划。

2. 将 `standard_requirement.md` 真正接入流程门禁。
   `REQUIREMENT_PARSE` 现在在已有文档和新生成文档两条路径上都会执行严格校验，失败则直接阻断流程。

3. 收紧 `review_report_xx.md` 的问题清单质量要求。
   每个问题现在必须包含：
   文件路径、行号、明确根因、明确修复建议。
   不能再只写“某处有问题，请修复”这类空泛描述。

4. 增加最终验收阶段 readiness guard。
   `FINAL_ACCEPTANCE` 现在会在进入前检查：
   是否存在 `sprint_plan.md`；
   所有计划内 Sprint 是否都已完成；
   是否仍有当前进行中的 Sprint。

这一批解决的核心问题：

1. “标准化需求只是形式存在，没有最小可开发语义”。
2. “评审问题清单不能真实指导修复代码”。
3. “流程走到了最终验收，但业务上其实还有 Sprint 没完成”。

## 5. 当前已经形成的闭环

截至当前，下面这些领域已经从“文档要求”初步升级为“规则闭环”：

### 5.1 运行时硬门禁

已经具备明确 guard 的主要领域：

1. 受保护分支提交
2. 评估硬阈值
3. 规划失败中断
4. 预验收交付物门禁
5. 最终验收报告完整性和结论门禁
6. 发布前证据门禁
7. 状态机非法跳转阻断
8. 最终验收 readiness 校验

### 5.2 反作弊测试

已经覆盖的典型反作弊场景包括：

1. 文案写“通过”，但维度分数或整体均分不达标。
2. 规划文档一直不合格，但流程试图继续。
3. 合同存在、源码存在，但核心交付物缺失。
4. 最终验收报告存在，但不完整或结论不通过。
5. 评审报告只有一个问题壳子，没有文件/行号/根因/修复建议。
6. 状态机试图从不合法状态直接跳到后续阶段。

### 5.3 开发指导能力

和最初相比，当前测试已经更接近“可指导开发”的状态，主要体现在：

1. 很多失败信息已经能直接指出是哪条结构或行为规则未满足。
2. 一批关键规则已经能通过行为测试暴露真实实现缺口，而不是只暴露文案差异。
3. “为了测试而测试”的空间被明显压缩。

## 6. 目前还剩什么

虽然已经完成 6 批，但距离最终目标仍有差距，主要集中在下面几类。

### 6.1 恢复链路还不够精细

当前还需要继续收紧：

1. checkpoint 恢复后的阶段判断精度
2. Sprint 子状态恢复后的执行路径一致性
3. 恢复后哪些阶段该重跑、哪些阶段必须跳过的明确规则

风险：

如果这部分不继续收紧，系统仍可能在“中断恢复”场景下出现跳过剩余工作、重复执行错误阶段或恢复后状态与实际产物不一致的问题。

### 6.2 阶段后置条件还不够系统化

当前虽然已经有一些阶段门禁，但还没有把所有关键阶段都补成统一的：

1. pre-condition
2. action
3. post-condition

完整模式。

还需要继续补的不是“再多写 if”，而是把阶段完成定义做成明确、可复用、可测试的规则集。

### 6.3 结构化交接还没有完全 schema 驱动

当前已经从“纯章节存在性”进步到“部分语义可校验”，但还没有完全达到：

1. 结构化输入对象生成
2. 结构化对象校验
3. 结构化对象驱动后续阶段

这种强闭环。

当前仍有一部分逻辑是从 Markdown 文本中提取结构，属于过渡阶段。

### 6.4 少量测试仍偏静态契约检查

当前仍有一些测试主要做：

1. 源码字符串存在性检查
2. prompt 契约检查
3. 模板存在性检查

这些测试不是没有价值，但它们不足以单独承担“严格指导开发”的职责，后续还需要继续替换成行为测试。

## 7. 后续将要做的事情

### 7.1 第七批：恢复链路与阶段级后置条件

这一批建议作为下一优先级。

目标：

1. 收紧 checkpoint 恢复逻辑。
2. 精确处理 Sprint 子状态恢复。
3. 为关键阶段增加 post-condition 校验。

重点方向：

1. 恢复后不能误跳过未完成 Sprint。
2. 恢复后状态、产物、Git、checkpoint 必须一致。
3. 阶段“完成”必须有明确定义，而不是只看流程走到了下一步。

期望结果：

1. 中断恢复场景更可预测。
2. 状态机不只“禁止乱跳”，还能够“精确恢复”。
3. 失败信息能明确告诉开发者缺少哪类阶段完成证据。

### 7.2 第八批：结构化交接继续收紧

这一批建议在第七批之后做。

目标：

1. 继续收紧合同、评审、发布证据等核心产物。
2. 减少对 Markdown 自由文本解析的依赖。
3. 让结构化对象真正驱动流程。

重点方向：

1. 合同结构进一步标准化。
2. 评审报告从“文本中抽取问题”继续推进到更稳定的结构格式。
3. 发布证据和项目总结进一步具备可程序消费的结构。

期望结果：

1. 结构化交接不再只是“看起来有结构”。
2. 后续阶段更少依赖宽松文本匹配。
3. 测试可以更直接地校验对象级规则。

### 7.3 持续清理项：把剩余静态测试继续替换为行为测试

这不是单独一批，而是后续每批都应持续做的工作。

重点方向：

1. 减少纯 `toContain(...)` 式规则验证。
2. 增加真实运行路径上的输入-输出断言。
3. 每个关键规则都补反作弊场景。

## 8. 建议的后续执行顺序

建议保持下面这个顺序继续推进：

1. 先做第七批，先把恢复链路和阶段 post-condition 补齐。
2. 再做第八批，把结构化交接继续从“可解析”推进到“强结构化”。
3. 每完成一批，就顺手清理该批相邻模块中的静态测试。

这样做的原因是：

1. 恢复链路和阶段后置条件会直接影响流程正确性。
2. 结构化交接的进一步收紧需要建立在更稳定的阶段边界之上。
3. 如果顺序反过来，可能会出现“对象结构更强了，但恢复和阶段完成定义仍然松”的不协调状态。

## 9. 当前结论

如果用一句话概括当前状态：

测试体系已经从“覆盖面很大的审查清单”升级成了“开始具备强约束力的可执行规范”，但还没有完全达到“开发只跟着测试走就一定能走到最终正确实现”的终局状态。

更具体地说：

1. 已完成部分，已经能明显限制“为了测试而测试”的实现。
2. 剩余差距，主要集中在恢复精度、阶段完成定义和更强的结构化交接。
3. 后续工作不再是大面积铺测试，而是继续把剩余关键路径收紧成 guard + 行为测试 + 证据三层闭环。
