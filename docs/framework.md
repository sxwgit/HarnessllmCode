# 自主代码开发多智能体Harness框架 工程化落地执行Prompt v3.1（修正版·不含扩展性优化）
**文档版本**：v3.1 元程序/程序全隔离修正版（仅修复架构/工程化/协作/异常/观测/安全问题，**未修改多项目/云原生扩展性**）
**核心对齐**：Anthropic《Harness design for long-running application development》核心工程化理念
**执行目标**：基于用户提供的`idea.md`，通过**元程序与目标程序全维度隔离**、多智能体权责分离、生成-评估对抗闭环，实现无人工干预的全流程工程化代码自主开发、迭代与交付
**生效范围**：本Prompt为元程序全生命周期、目标程序构建全流程的唯一执行准则，所有模块、智能体必须100%严格遵守，严禁突破任何强制约束与硬阈值规则

## 一、不可突破的核心执行铁则（全流程强制执行）
以下规则为框架运行的底层逻辑，任何场景下严禁修改、绕过，违反任意一条即触发流程终止与异常告警
### 第一类：基础运行铁则（全流程不可突破）
1.  **权责完全分离铁则**：代码生成与质量评估彻底解耦，分别由独立智能体负责，严禁同一智能体既做代码生成又做验收评估，完全遵循GAN式生成-评估对抗逻辑
2.  **结构化产物唯一交接铁则**：所有智能体间、模块间的信息传递，仅能通过Git仓库中标准化、带固定Schema的结构化产物（Artifact）完成，严禁通过对话上下文传递核心信息
3.  **上下文轻量化重置铁则**：每一次智能体调用，均为全新的干净会话，仅传入当前任务所需的指定结构化产物+**Sprint核心轻量化上下文**，严禁携带全量历史对话、非当前任务相关的上下文信息
4.  **全链路Git可追溯铁则**：每一次决策、每一行代码变更、每一轮评估、每一次异常处理，必须生成对应的Git提交记录，严禁任何脱离Git管控的操作；所有版本回退仅能使用`git revert`，**批量回退需执行提交整理**，严禁使用`git reset --hard`等破坏时间线的操作
5.  **Sprint合同前置+预验收铁则**：每个Sprint开发前，必须完成Generator与Evaluator的Sprint合同协商并达成100%一致；开发完成后需先通过**预验收校验**，未签署生效的Sprint合同、未通过预验收，严禁进入正式验收阶段
6.  **评估硬阈值一票否决铁则**：Evaluator验收采用一票否决制，任何一个验收维度得分＜6分，或整体平均分＜7分，直接打回修复，严禁降低验收门槛、放水通过
7.  **最小人工干预+审计铁则**：仅本Prompt明确约定的极端异常场景可触发人工通知，99%的开发、迭代、排障、回退动作必须由框架自主完成；**所有人工操作必须纳入Git审计与日志记录**，严禁随意触发人工介入
8.  **无直接通信+反向反馈铁则**：Planner、Generator、Evaluator三个核心智能体之间严禁直接对话，所有信息传递必须通过Harness主编排器中转；**Evaluator可通过编排器向Planner发起架构级反向反馈**，严禁权责交叉、越权操作
9.  **安全沙箱最小权限铁则**：所有工具集、智能体操作仅能在目标程序沙箱内执行，遵循最小权限原则，严禁执行高危系统命令、越权访问目录，在代码或者prompt中如果有任何对路径的描述、操作，必须说明是什么路径？元程序路径或者程序路径，保证任何写入的安全，可靠。
10. **双仓实时隔离监控铁则**：全流程实时监控元程序/目标程序隔离状态，**发现跨仓违规操作立即暂停流程**，严禁隔离失效后继续执行

### 第二类：元程序/程序双隔离铁则（全流程不可突破）
11.  **物理+权限双重隔离铁则**：元程序与目标程序必须存储在完全独立的目录路径下，优先采用同级目录隔离方案；特殊场景需嵌套时必须严格配置`.gitignore`+**目录只读权限**实现100%隔离，两者的文件操作、环境运行、Git仓库完全独立，严禁路径重叠
12. **Git双仓独立铁则**：元程序与目标程序必须使用**完全独立的双Git仓库**，各自有独立的分支策略、提交规范、回退规则，严禁跨仓库操作、严禁将目标程序代码提交到元程序Git、严禁将元程序代码提交到目标程序Git
13. **操作权责隔离铁则**：构建过程中的所有智能体、工具集仅能操作**目标程序目录与目标程序Git仓库**，绝对禁止修改、删除、读写元程序的任何文件、配置、Git仓库；元程序的修改仅能通过框架开发者的版本管理流程完成，与目标程序构建流程完全解耦
14. **高危操作双禁铁则**：元程序Git与目标程序Git均**严禁执行`git reset --hard`、`git rm -rf .git`、删除.git目录、强制推送覆盖远程分支等破坏时间线的高危操作**，所有版本变更必须保留完整可追溯的时间线
15. **状态日志双存+结构化铁则**：元程序运行状态与目标程序构建状态、元程序运行日志与目标程序构建日志，必须分别持久化到独立的文件与目录中，**日志统一采用JSON结构化格式**，严禁状态混淆、日志交叉、跨文件读写

## 二、核心定义与强制边界划分
### 2.1 核心定义（严格区分，无歧义）
| 类型 | 官方全称 | 核心定义 | 核心用途 | 变更/操作主体 |
|------|----------|----------|----------|--------------|
| **元程序** | Meta-Program（Harness框架） | 构建程序的程序，即本Harness框架本身，是整个自主开发流程的唯一执行载体 | 自主完成目标程序的需求解析、规划设计、代码生成、验收评估、迭代交付全流程，管控整个构建生命周期 | 仅能通过框架开发者的版本管理流程变更，目标程序构建过程中严禁任何修改、读写操作 |
| **目标程序** | Target-Project（被构建项目） | 被元程序构建的目标项目，即用户`idea.md`需求对应的最终交付应用 | 实现用户业务需求的可运行应用代码、配置、文档、测试用例等完整交付物 | 由元程序的Generator智能体开发、Evaluator智能体验收，全流程由元程序管控，仅能在目标程序专属目录与Git仓库内操作 |

### 2.2 强制权责边界清单
| 操作/资源 | 元程序专属 | 目标程序专属 | 严禁交叉操作 |
|-----------|------------|--------------|--------------|
| 目录路径 | 元程序根目录（含所有子目录，**构建期设为只读**） | 目标程序根目录（含所有子目录） | 智能体、工具集严禁读写元程序目录，元程序严禁将核心文件写入目标程序目录 |
| Git仓库 | 元程序专属Git仓库（仅管理框架代码） | 目标程序专属Git仓库（仅管理项目代码） | 严禁跨仓库提交、合并、读写配置，严禁两个仓库出现嵌套或重叠 |
| 配置文件 | 元程序配置（`harness_config.json`、Prompt模板、框架参数，**敏感信息加密存储**） | 目标程序配置（项目依赖、应用配置、业务参数） | 严禁修改对方配置文件，严禁配置交叉写入 |
| 智能体操作 | 无（智能体由元程序启动，但无元程序操作权限） | 需求解析、规划设计、代码开发、验收评估、迭代优化 | 智能体严禁执行任何元程序相关的操作 |
| 状态文件 | `meta_state.json`（元程序运行状态） | `project_state.json`（目标程序构建状态） | 严禁跨文件读写、状态合并 |
| 日志文件 | `meta_logs/`（元程序运行日志，**JSON结构化**） | `project_logs/`（目标程序构建日志，**JSON结构化**） | 严禁日志交叉归档、跨目录写入 |

### 2.3 强制目录结构规范
#### 方案一：同级物理隔离方案（最优推荐，零Git冲突风险）
元程序与目标程序存储在**同级独立目录**下，完全避免路径重叠、Git嵌套冲突，为强制首选方案
```
# 父级工作根目录（无Git仓库，仅用于存放元程序与目标程序）
workspace_root/
├── harness_meta/              # 元程序根目录（专属独立Git仓库，构建期只读）
│   ├── .git/                  # 元程序专属Git仓库（构建过程中只读，严禁修改）
│   ├── .gitignore             # 元程序Git忽略配置（强制配置）
│   ├── harness_config.json    # 元程序核心配置文件（加密存储，纳入元程序Git）
│   ├── prompts/               # 智能体Prompt模板目录（纳入元程序Git）
│   │   ├── planner_system.md
│   │   ├── generator_system.md
│   │   └── evaluator_system.md
│   ├── src/                   # 元程序框架核心代码（纳入元程序Git）
│   │   ├── orchestrator/      # Harness主编排器（核心大脑，含降级容错机制）
│   │   ├── agents/            # 多智能体管理模块
│   │   ├── dual_git_manager/  # 双仓Git管控模块（隔离核心+实时监控）
│   │   ├── tools/             # 标准化工具集模块（最小权限沙箱）
│   │   └── exception/         # 异常处理模块（分级自愈+自优化）
│   ├── meta_logs/             # 元程序运行日志目录（元程序Git忽略，JSON结构化）
│   └── meta_state.json        # 元程序全局状态文件（元程序Git忽略）
│
└── target_project/            # 目标程序根目录（专属独立Git仓库，元程序初始化）
    ├── .git/                  # 目标程序专属Git仓库（元程序全程管控）
    ├── .gitignore             # 目标程序Git忽略配置（强制配置）
    ├── idea.md                # 用户原始需求（只读，元程序复制写入）
    ├── standard_requirement.md # 标准化需求文档（元程序输出）
    ├── docs/                  # 目标程序结构化产物目录（纳入目标程序Git）
    │   ├── plan/              # Planner输出的设计文档
    │   ├── sprint/            # Sprint合同、评审报告
    │   └── report/            # 验收报告、度量报告
    ├── src/                   # 目标程序业务代码目录（Generator唯一可操作目录）
    ├── test/                  # 目标程序测试用例目录
    ├── project_logs/          # 目标程序构建日志目录（目标程序Git忽略，JSON结构化）
    └── project_state.json     # 目标程序构建状态文件（目标程序Git忽略）
```

#### 方案二：嵌套目录隔离方案（仅环境限制时使用，需严格配置）
若因环境限制必须将目标程序嵌套在元程序目录下，必须严格配置`.gitignore`+**目录权限管控**实现100%隔离，严禁目标程序内容进入元程序Git
```
harness_meta/                  # 元程序根目录（专属独立Git仓库，构建期只读）
├── .git/                      # 元程序专属Git仓库
├── .gitignore                 # 强制完全忽略目标程序目录
├── harness_config.json        # 加密存储，纳入元程序Git
├── prompts/
├── src/
├── meta_logs/                 # JSON结构化日志
├── meta_state.json
└── target_project/            # 目标程序根目录（嵌套存放，专属独立Git仓库，权限隔离）
    ├── .git/                  # 目标程序专属Git仓库
    ├── .gitignore
    ├── idea.md
    ├── docs/
    ├── src/
    ├── project_logs/          # JSON结构化日志
    └── project_state.json
```

## 三、整体架构与分层执行契约
本框架采用**1核3体4层**分层解耦架构，新增**容错降级、反向反馈、预验收校验**能力，完全对齐Anthropic Harness设计范式，同时全链路嵌入元程序/目标程序隔离能力，每层职责、输入输出、交互规则完全标准化，层间仅能通过Harness主编排器完成交互，严禁跨层直接通信

### 3.1 架构总览
```
┌─────────────────────────────────────────────────────────────┐
│                      接入层 (Access Layer)                   │
│  元程序专属：需求读取、环境初始化、人工通知、最终产物交付    │
├─────────────────────────────────────────────────────────────┤
│              核心编排层 (Orchestrator Layer)                │
│  元程序核心：全流程调度、状态管理、智能体生命周期控制、异常处理│
│  【Harness核心】：含SPOF降级、反向反馈、断点续跑快照管理     │
├─────────────────────────────────────────────────────────────┤
│              多智能体层 (Multi-Agent Layer)                 │
│  元程序驱动、仅操作目标程序：【Planner】→【Generator】→【Evaluator】
│  新增：预验收模块、轻量化上下文、技术栈插件适配              │
├─────────────────────────────────────────────────────────────┤
│              基础能力层 (Infrastructure Layer)               │
│  元程序专属：双仓Git管控、工具集、上下文管理、日志系统、配置中心│
│  新增：实时隔离监控、安全沙箱、结构化日志、自优化引擎        │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 分层模块执行契约（含隔离规则）
| 层级 | 模块名称 | 核心执行职责 | 标准化输入 | 标准化输出 | 隔离强制规则 |
|------|----------|--------------|------------|------------|--------------|
| 接入层 | 需求解析模块 | 读取用户`idea.md`，完成需求完整性校验、标准化格式转换，仅在需求完全无法解析时触发人工介入 | 父级工作目录下的`idea.md` | 标准化后的`standard_requirement.md`（写入目标程序根目录） | 仅能将标准化需求写入目标程序目录，严禁修改元程序文件 |
| 接入层 | 双环境初始化模块 | 分别完成元程序自检、目标程序环境初始化，**新增权限隔离校验**，保障双环境隔离与一致性 | 元程序配置文件、标准化需求文档 | 环境校验报告、初始化完成的目标程序目录与Git仓库 | 目标程序环境初始化仅能在目标程序目录内执行，严禁触碰元程序环境；元程序环境仅做自检+只读锁定，严禁构建过程中修改 |
| 核心编排层 | Harness主编排器 | 框架唯一大脑，**新增SPOF降级、反向反馈、状态重试阈值管控**，负责全流程状态流转、步骤调度、智能体生命周期控制、异常处理、迭代闭环控制，所有信息中转唯一通道 | 双环境校验报告、全流程结构化产物、状态机当前状态 | 智能体调用指令、状态流转指令、异常处理指令、流程闭环控制指令 | 仅能向智能体传入目标程序相关的结构化产物，严禁泄露元程序文件路径与内容；所有调度指令必须符合隔离规则 |
| 核心编排层 | 双状态管理模块 | 元程序状态、目标程序构建状态的独立持久化管理，**新增状态快照、断点续跑规则** | 各模块执行结果、状态变更指令 | `meta_state.json`、`project_state.json`、**状态快照文件** | 两个状态文件完全独立存储、独立读写，严禁状态合并、交叉写入 |
| 多智能体层 | Planner Agent 规划师 | 需求拆解、产品规格定义、技术架构设计、Sprint计划拆分、代码规范制定，**接收Evaluator架构反向反馈**，仅做高层设计，严禁编写具体代码实现 | 标准化需求文档、前序迭代架构优化建议、**Evaluator架构反馈报告** | 5份结构化设计文档（固定Schema，写入目标程序`docs/plan/`目录） | 仅能读写目标程序目录下的文件，输出产物仅能写入目标程序指定目录，严禁触碰元程序 |

## 四、全流程有限状态机（FSM）与强制流转规则
本框架全流程必须严格遵循以下有限状态机执行，**新增状态重试阈值、合并后校验、断点续跑快照**，每个状态的进入条件、执行动作、隔离校验规则、成功流转路径、失败异常路径完全固定，严禁跳步、逆序、私自修改流转规则

### 4.1 状态枚举与全流程流转总图
```
[META_INIT 元程序自检状态] → [PROJECT_INIT 目标程序初始化状态] → [REQUIREMENT_PARSE 需求解析状态]
→ [PLANNING 规划设计状态] → [SPRINT_DISPATCH 任务分发状态] → [SPRINT_NEGOTIATION Sprint合同协商状态]
→ [DEV 代码开发状态] → [PRE_EVALUATION 预验收状态] → [EVALUATION 验收评估状态]
→ 【验收通过】→ [SPRINT_MERGE 合并状态] → 【合并后编译测试】→ 【所有Sprint完成】→ [FINAL_ACCEPTANCE 全量验收状态]
→ [RELEASE 交付发布状态] → [FINISHED 流程完成状态]
【任意环节失败】→ [EXCEPTION_HANDLE 异常处理状态] → 【可自愈】→ 返回失败前状态重试（**达阈值则升级**）
→ 【不可自愈】→ [MANUAL_INTERVENTION 人工介入状态（带审计）]
```

## 五、双Git仓库独立管控与强制版本规则
### 5.1 双Git仓库基础规则
1.  **仓库独立原则**：元程序Git仓库与目标程序Git仓库必须完全独立，严禁出现Git仓库嵌套、共用、交叉提交的情况
2.  **操作权限原则**：构建过程中，元程序Git仓库仅支持只读操作，严禁任何写入、修改、合并、回退操作；目标程序Git仓库由双仓Git管控模块全程管控，仅能执行本Prompt允许的操作
3.  **高危操作双禁+提交整理原则**：两个仓库均严禁执行`git reset --hard`、`git rm -rf .git`、删除.git目录、强制推送覆盖远程分支等破坏时间线的高危操作；**批量revert需执行提交整理，避免记录膨胀**，所有版本变更必须保留完整可追溯的时间线
4.  **隔离实时校验原则**：**Git操作前+运行中实时**执行隔离校验，确认操作的仓库、分支、目录符合隔离规则，校验不通过/发现违规立即暂停流程

### 5.2 元程序Git仓库管理规则（框架开发者专用，构建过程只读）
| 管理项 | 强制规则 |
|--------|----------|
| 核心用途 | 仅管理元程序框架代码、配置文件、Prompt模板、架构设计文档 |
| 分支策略 | 由框架开发者独立定义，构建过程中不做任何修改 |
| 提交规范 | 由框架开发者独立定义，构建过程中严禁任何提交 |
| 版本回退 | 仅能由框架开发者在非构建时段执行，严禁构建过程中执行任何回退操作 |
| 构建期权限 | 只读+锁定，严禁任何写入、修改、合并操作 |

### 5.3 目标程序Git仓库管理规则（元程序全程管控）
#### 5.3.1 分支管理强制策略
| 分支名称 | 分支类型 | 保护规则 | 核心用途 | 创建与合并规则 |
|----------|----------|----------|----------|----------------|
| `main` | 主分支 | 严格保护，仅允许全量验收通过的代码合并，不允许直接提交、不允许强制推送 | 存放目标程序稳定发布版本，每个合并版本都有对应的发布Tag | 仅能从目标程序`dev`分支合并，合并前必须完成全量验收，合并后必须打正式发布Tag |
| `dev` | 开发主分支 | 保护，仅允许验收通过的Sprint分支合并，不允许直接提交 | 存放目标程序开发过程中的最新稳定版本，每个Sprint完成后合并一次 | 仅能从目标程序`sprint/xx`分支合并，合并前必须验证Sprint验收通过、代码可正常运行，合并后必须打里程碑Tag |
| `sprint/xx` | 临时开发分支 | 无保护，仅用于单个Sprint的开发、迭代、修复 | 每个Sprint创建一个专属分支，验收通过后合并到`dev`分支并删除 | Sprint启动前基于最新`dev`分支创建，Sprint验收通过后合并到`dev`分支，合并完成后自动删除 |
| `fix/xx` | 修复分支 | 无保护，用于连续迭代失败后的回退修复 | 当Sprint连续迭代失败，创建该分支基于**最近稳定里程碑Tag**重新开发 | 基于**最近稳定里程碑Tag**创建，修复完成验收通过后合并到`dev`分支 |
| `feat/xx` | 特性分支 | 无保护，用于架构设计、文档编写等非开发任务 | 用于规划阶段、架构修订阶段的文档提交 | 基于`dev`分支创建，文档校验通过后合并到`dev`分支 |

#### 5.3.2 提交信息强制规范
所有Git提交必须严格遵循以下格式，不符合格式的提交自动驳回，严禁无意义提交；**人工操作提交需标注manual-fix**
```
<proj-type>(<proj-scope>): <description>
```
- **proj-type强制枚举**：仅允许使用以下类型，严禁自定义
  - `feat`：新功能开发
  - `fix`：bug修复
  - `docs`：文档变更、结构化产物输出
  - `style`：代码规范调整，不影响代码逻辑
  - `refactor`：代码重构，不新增功能、不修复bug
  - `test`：测试用例新增/修改
  - `init`：项目初始化、环境初始化
  - `revert`：版本回退
  - `manual-fix`：人工介入修复（仅人工操作使用）
- **proj-scope强制枚举**：仅允许使用以下范围，严禁自定义
  - `sprint-xx`：对应Sprint的变更
  - `architecture`：架构设计、规划相关变更
  - `planner`：Planner智能体相关输出
  - `generator`：Generator智能体相关代码变更
  - `evaluator`：Evaluator智能体相关报告输出
  - `project`：目标项目全局变更

#### 5.3.4 自动回退强制执行规则
所有回退操作必须生成完整的审计日志，记录回退触发原因、回退前后版本号、操作时间、影响范围，严禁无记录回退；**批量回退自动执行提交整理**，所有回退仅能使用`git revert`
1.  **Sprint级回退触发条件与执行步骤**
    - 触发条件：单个Sprint连续3次迭代验收不通过
    - 执行步骤：① 暂停当前Sprint开发；② 输出回退日志与原因分析；③ 使用`git revert`将`sprint/xx`分支重置到该Sprint启动前的`dev`分支稳定状态；④ **批量revert自动整理提交**；⑤ 清空无效修改，重新开始该Sprint的开发
2.  **架构级回退触发条件与执行步骤**
    - 触发条件：架构设计缺陷导致多个Sprint受阻，Evaluator触发架构修订流程

3.  **灾难性回退触发条件与执行步骤**
    - 触发条件：代码仓库混乱、分支冲突无法解决、无法正常迭代的极端场景
    - 执行步骤：① 暂停框架运行；② 输出完整异常报告；③ 使用`git revert`一键回退到规划完成后的`v0.1.0-plan-complete`里程碑Tag；④ **批量revert自动整理提交**；⑤ 重置所有临时分支，重新开始Sprint执行

2.  未通过工具实际运行测试、安全扫描就给出验收结论，视为无效验收，触发重新执行
3.  输出路径不符合要求，视为无效输出，触发重新生成
4.  放水通过不符合硬阈值的代码，直接触发流程回退，重新执行验收

## 七、自适应异常分级处理与鲁棒性规则
### 7.1 异常分类与强制隔离处理规则
| 异常类型 | 定义 | 影响范围 | 处理主体 | 强制隔离处理规则 | 最大重试次数 |
|----------|------|----------|----------|------------------|--------------|
| 元程序异常 | 元程序框架自身的异常（如编排器故障、工具集失效、元程序Git异常） | 可能导致整个目标程序构建流程终止 | 元程序异常处理模块 | 1. 立即暂停目标程序构建流程；2. 保存当前目标程序状态与Git快照；3. 输出元程序异常报告到元程序日志目录；4. 触发人工通知（元程序异常仅能由框架开发者处理）；5. 严禁在处理过程中修改目标程序Git与代码 | 0次，直接触发人工介入 |
| 目标程序异常 | 目标程序构建过程中的异常，与元程序无关 | 仅影响当前目标程序构建流程，不影响元程序 | 元程序异常处理模块（针对目标程序） | 1. 仅在目标程序目录与Git仓库内执行处理操作；2. 严禁修改元程序任何文件与Git仓库；3. 所有处理动作记录到**JSON结构化**目标程序日志；4. 处理完成后仅更新目标程序状态；5. **自愈完成后触发规则自优化** | 按异常等级执行 |

### 7.2 目标程序异常分级（P0-P4）与强制处理规则
根据异常影响范围、严重程度，将目标程序异常分为**P0（灾难性）-P4（提示）** 五个等级，每个等级的处理流程完全固定，严禁越级处理
| 异常等级 | 异常严重程度 | 典型异常场景 | 强制处理流程 | 最大重试次数 |
|----------|--------------|--------------|--------------|--------------|
| P0 灾难性 | 全流程阻断，无法自愈 | 1. 连续2次Sprint回退仍失败；2. 需求完全无法解析；3. 架构设计连续3次生成失败；4. 目标程序Git仓库损坏、环境完全不可用；5. 全量验收连续2次不通过 | 1. 立即暂停框架全流程运行；2. 输出完整异常报告、当前目标程序状态、上下文信息、根因分析；3. 触发人工通知+**审计记录**；4. 等待人工处理指令；5. 仅能通过人工指令恢复或终止流程 | 0次，直接触发人工介入 |
| P1 严重 | 单个Sprint阻断，需回退 | 1. Sprint连续3次迭代验收不通过；2. 代码合并冲突无法自动解决；3. 架构设计局部缺陷；4. 环境异常无法自动修复 | 1. 暂停当前环节执行；2. 输出异常报告与根因分析；3. 触发对应级别的版本回退（仅使用git revert）；4. 回退完成后重新执行当前环节；5. 更新目标程序状态；6. **自愈后规则自优化** | 2次回退 |
| P2 一般 | 单个环节阻断，可迭代修复 | 1. 智能体输出产物缺失必填模块；2. 代码自检查不通过；3. 单次Sprint验收不通过；4. 编译/运行时非阻断性异常 | 1. 记录异常详情与日志；2. 输出修复指引，打回对应智能体修复；3. 修复完成后重试当前环节；4. 更新目标程序状态；5. **自愈后规则自优化** | 3次 |
| P3 轻微 | 不影响流程，可自动修复 | 1. 智能体输出格式错误、缺失非核心字段；2. 工具调用超时、临时网络异常；3. Git提交冲突可自动解决；4. 代码轻微语法错误 | 1. 记录异常日志到目标程序日志目录；2. 自动重试对应操作；3. 重试成功后继续流程；4. 更新目标程序状态 | 3次 |
| P4 提示 | 无影响，仅记录 | 1. 非关键日志缺失；2. 低风险安全提示；3. 非核心文档格式不规范 | 1. 记录日志；2. 不中断流程；3. 后续自动优化 | 0次 |

### 7.3 自适应阈值调整规则
为匹配不同复杂度的Sprint任务，框架自动基于Sprint工作量评估值，调整重试次数与迭代阈值，严禁固定不变的阈值
| Sprint工作量评估值（10分制） | 单Sprint最大迭代次数 | 最大回退次数 | 协商超时轮次 |
|------------------------------|------------------------|--------------|--------------|
| 1-3分（简单任务） | 2次 | 1次 | 2轮 |
| 4-7分（中等任务） | 3次 | 2次 | 3轮 |
| 8-10分（复杂任务） | 4次 | 2次 | 4轮 |

### 7.4 通用异常兜底+自优化规则
1.  所有异常必须生成完整的**JSON结构化**日志记录，包含异常时间、异常等级、触发场景、根因分析、处理动作、处理结果，无日志的异常处理视为无效操作
2.  单个环节连续3次处理失败，自动升级异常等级，触发更高级别的处理流程
3.  框架运行过程中，实时监控token消耗、运行耗时、资源占用，超过预设阈值自动触发告警，优化上下文传入策略
4.  所有智能体调用、工具调用必须设置超时时间，超时自动中断，避免无限等待
5.  临时工作区内容，单次会话结束后自动清理，避免资源泄露、上下文污染
6.  全流程每个关键节点必须执行双仓隔离校验，发现违规操作立即暂停流程，触发异常告警
7.  **异常自愈完成后，自动归档根因，优化执行规则，避免同类异常重复发生**
8.  人工介入操作必须生成**审计日志+Git标注提交**，确保全链路可追溯

## 十、框架生效与版本管理规则
### 10.1 框架生效范围
本框架为元程序全生命周期、目标程序构建全流程的唯一执行准则，自发布之日起生效，所有模块、智能体、工具集必须100%严格遵守，严禁突破任何强制约束与硬阈值规则。
任何场景下，本框架的强制铁则、硬阈值规则、隔离规则为最高优先级，严禁任何模块、智能体以任何理由绕过、修改、降低标准。

### 10.2 框架版本管理规则
1.  本框架版本号采用「主版本号.次版本号.修订号」规则，主版本号为架构级变更，次版本号为核心规则新增/调整，修订号为细节优化与bug修复。
2.  框架所有版本变更必须纳入元程序Git仓库版本管控，每次变更必须记录完整的变更日志，明确变更内容、影响范围、生效时间。
3.  单个目标项目构建过程中，严禁切换框架版本，确保全流程执行规则的一致性；仅能在项目构建完成后，升级框架版本用于新项目构建。
4.  框架版本变更严禁修改核心隔离铁则、权责分离铁则、全链路可追溯铁则，确保核心架构的稳定性。

### 10.3 合规校验规则
1.  全流程每个关键节点必须执行框架合规校验，校验内容包含：隔离规则执行情况、权责分离执行情况、Git管控规则执行情况、硬阈值规则执行情况。
2.  合规校验不通过的环节，必须立即暂停流程，触发异常处理，整改完成后才可继续执行。
3.  项目交付前必须执行全流程合规校验，合规率100%才可视为项目交付完成。

### 10.4 兜底规则
本框架未明确约定的场景，必须遵循以下兜底规则执行，严禁私自拓展规则边界：
1.  所有操作必须优先保障元程序与目标程序的双仓隔离，严禁任何可能突破隔离的操作。
2.  所有操作必须保障目标程序Git时间线的完整性，严禁任何破坏可追溯性的操作。
3.  所有智能体操作必须严格遵循权责分离原则，严禁越权操作、交叉执行。
4.  所有异常场景必须优先保障目标程序代码的安全性，严禁无记录的代码修改、版本回退。
5.  所有人工介入操作必须纳入审计与Git管控，严禁无记录的人工修改。
