# 测试用例文档生成Prompt
---
## 【核心任务】
你需要严格基于指定的**预期实现框架文档**，生成一份完整、规范、可落地的**测试用例全文档**。
> 明确说明：最终输出是结构化的测试用例文档，文档核心主体为标准化的测试用例集；禁止输出零散、无结构的单条测试用例，也禁止输出与测试用例无关的文档内容。

## 【前置依赖与最高优先级规则】
1.  唯一基准依据：`<workspace-path>` 预期实现框架文档
    - 所有测试用例的测试目标、预期结果，必须100%对齐该框架文档的要求，不得做任何偏离、妥协或自主修改
2.  仅作参考内容：`<workspace-path>` 现有实现路径
    - 现有实现仅作业务上下文参考，**绝对禁止作为用例设计的依据**；你必须默认现有实现可能存在与预期框架不符的缺陷、遗漏或错误，不得因现有实现的内容调整用例的预期结果
3.  底线要求：即使最终用例在现有实现上执行结果为失败，也完全可接受；但绝对不允许出现用例设计逻辑错误、预期结果与框架不符、用例无法执行等异常问题。

## 【测试用例文档必须包含的完整结构】
请按以下固定结构生成文档，不得遗漏核心模块：
1.  文档概述：说明文档的测试范围、测试对象、参考依据、测试类型与适用场景
2.  测试环境说明：明确用例执行的基础环境依赖、前置准备事项
3.  测试模块拆分：基于预期实现框架，拆解出完整的测试模块/功能点层级，明确各模块的测试范围
4.  核心测试用例集：文档主体，按模块分类输出标准化测试用例
5.  测试执行说明：包含用例优先级规则、执行顺序建议、结果判定标准
6.  风险与备注说明：针对框架中未明确的边界点、潜在歧义点的补充说明与用例设计原则

## 【测试用例设计核心原则】
1.  **测试目标绝对明确**
    每条用例必须对应唯一、清晰的测试点，精准指向预期框架中的一项明确要求，禁止出现多目标混杂、目标模糊的用例。
2.  **测试维度全覆盖+拆分精细化**
    - 层级拆分：必须拆分为「单元级测试用例（最小功能点/方法级）」、「模块集成级测试用例（模块间交互）」、「端到端业务场景级测试用例（完整业务流程）」三个层级
    - 场景全覆盖：必须覆盖功能正常流程、边界值场景、异常输入/异常流程场景、容错与降级场景、权限/约束场景等全维度，无遗漏
3.  **用例完全独立**
    所有测试用例之间保持完全独立，单条用例可单独执行，无强依赖关系；一条用例的执行结果，不影响其他用例的执行与结果判定。
4.  **设计绝对严谨**
    用例的前置条件、测试步骤、预期结果必须无歧义、可复现、可量化；预期结果必须可被明确判定“通过/失败”，禁止出现模糊、主观的描述。

## 【单条测试用例标准化编写规范】
所有测试用例必须统一使用以下字段格式，不得缺省必填项：

| 字段名 | 必填/选填 | 字段说明 |
|--------|-----------|----------|
| 用例ID | 必填 | 全局唯一标识，格式：模块缩写_层级_序号（例：CORE_UNIT_001） |
| 所属模块 | 必填 | 对应框架中拆分的功能模块/子模块 |
| 测试类型 | 必填 | 单元测试/集成测试/场景测试/边界测试/异常测试等 |
| 用例优先级 | 必填 | P0（核心必测）/P1（重要功能）/P2（边缘场景） |
| 测试目标 | 必填 | 本条用例要验证的、来自预期框架的明确要求，一句话精准描述 |
| 前置条件 | 必填 | 执行本条用例必须满足的环境、数据、系统状态前提 |
| 测试步骤 | 必填 | 编号式、可1:1复现的操作步骤，每一步仅包含一个操作 |
| 预期结果 | 必填 | 与框架完全对齐的、每一步操作对应的明确输出/系统状态，可直接判定通过/失败 |
| 备注 | 选填 | 特殊说明、框架依据定位、风险提示等补充内容 |

## 【输出禁忌与最终要求】
1.  禁止自主编造框架中未提及的功能、规则与预期结果，所有用例必须有明确的框架文档依据
2.  禁止为了适配现有实现，修改、降低预期结果的标准
3.  禁止出现逻辑矛盾、步骤不可执行、预期结果模糊的无效用例
4.  输出保存为完整的markdown格式文档，结构清晰、层级分明，可直接用于测试执行与管理
5.  文档语言统一使用中文，专业术语与框架文档保持一致
