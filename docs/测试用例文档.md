## 一、文档概述

### 1.1 测试范围
本测试用例文档覆盖"自主代码开发多智能体Harness框架 v3.1"的**全部功能模块**，包括但不限于：
- 核心执行铁则（基础运行铁则10条 + 双隔离铁则5条）
- 核心定义与强制边界划分（元程序/目标程序双隔离体系）
- 四层架构与模块执行契约（接入层/核心编排层/多智能体层/基础能力层）
- 有限状态机FSM（13个状态的完整流转规则）
- 双Git仓库独立管控（分支策略/提交规范/Tag规则/回退规则）
- 多智能体标准化设计（Planner/Generator/Evaluator）
- 自适应异常分级处理（P0-P4异常分级 + 自优化）
- 全流程量化验收与效果度量（8项强制标准 + 15项度量指标）
- 结构化产物标准化模板（5个固定Schema模板）
- 框架生效与版本管理规则
- 请注意，你的测试用例应该运行因为功能代码不对导致的异常，后面功能代码自己优化。但是不能运行测试代码异常

### 1.2 测试对象
| 测试对象 | 说明 |
|----------|------|
| Harness框架整体 | 元程序（Harness框架本身）的全生命周期执行逻辑 |
| 编排器（Orchestrator） | 框架核心大脑，全流程调度、状态管理、智能体生命周期控制 |
| Planner Agent | 规划师智能体，需求拆解与高层设计 |
| Generator Agent | 生成器智能体，代码开发与bug修复 |
| Evaluator Agent | 评估师智能体，验收评估与质量把关 |
| 双仓Git管控模块 | 元程序/目标程序双Git仓库独立管理 |
| 工具集模块 | 标准化可调用工具，最小权限沙箱 |
| 双日志与监控模块 | 分级JSON结构化日志、实时监控 |
| 配置中心模块 | 加密只读配置管理 |
| 异常处理模块 | 分级自愈、自优化引擎 |
| 隔离监控模块 | 实时监控元程序/目标程序隔离状态 |
| 状态管理模块 | 双状态独立持久化、快照管理 |

### 1.3 测试类型与适用场景
| 测试类型 | 适用场景 |
|----------|----------|
| 单元测试 | 最小功能点/方法级验证，如单个铁则校验、单个状态流转、单个Git操作规范 |
| 集成测试 | 模块间交互验证，如编排器与智能体协作、Git管控与隔离监控联动 |
| 场景测试 | 完整业务流程验证，如从META_INIT到FINISHED的全流程模拟 |
| 边界测试 | 边界值场景验证，如重试阈值边界、评分阈值边界、异常等级升级边界 |
| 异常测试 | 异常输入/异常流程验证，如跨仓操作、高危命令执行、Git仓库损坏 |

## 二、测试环境说明

### 2.1 基础环境依赖
| 环境项 | 要求 |
|--------|------|
| 操作系统 | 支持Git的标准开发环境（Linux/macOS/Windows） |
| Git版本 | ≥ 2.0，支持分支策略、Tag、revert等标准操作 |
| Node.js | 按框架技术栈要求配置 |
| 运行环境 | 框架完整安装、依赖齐全、配置文件就绪 |
| 文件系统 | 支持目录权限管控（读/写/只读）、符号链接 |

### 2.2 前置准备事项
1. 准备独立的父级工作根目录（`workspace_root/`），确保无Git仓库
2. 准备有效的 `idea.md` 用户需求文件，放置于父级工作根目录
3. 确保元程序（`harness_meta/`）目录完整，包含所有核心文件：
   - `harness_config.json` 配置文件
   - `prompts/` 智能体Prompt模板目录
   - `src/` 框架核心代码目录
4. 确保目标程序（`target_project/`）目录不存在（用于测试初始化流程）
5. 准备测试用Git仓库环境，确保无残留分支、Tag
6. 确保文件系统支持权限管控操作（chmod等）
7. 备份所有测试前环境状态，确保测试可重复执行

### 6.1 框架中未明确的边界点

### 6.2 潜在歧义点说明

1. **"小步快跑"中"核心功能不超过3个"的定义**：本测试用例文档将"核心功能"定义为Sprint合同中明确列出的、带优先级的功能点清单项，非泛指的子功能
2. **"99%的自动化率"**：框架铁则第7条提到99%由框架自主完成，本测试用例文档将人工介入次数=0视为达标（仅在P0级灾难性异常允许人工介入）
3. **"JSON结构化日志"的具体字段**：框架要求统一包含时间戳、模块、状态、异常码、操作人、关键参数，本测试用例文档将这6个字段作为日志完整性校验的最低要求

### 6.3 用例设计原则补充

1. **独立性保证**：所有测试用例之间无强依赖关系，每条用例可单独执行，前置条件均已明确说明
2. **可复现性保证**：每条用例的测试步骤均为编号式、可1:1复现的操作，预期结果可明确判定通过/失败
3. **框架对齐保证**：所有用例的预期结果100%对齐framework.md，不得因现有实现调整预期结果标准
4. **不降低标准**：即使用例在现有实现上执行失败也完全可接受，但不允许出现用例设计逻辑错误
