# 严格化改造进展与后续路线图

更新时间：2026-04-14

## 1. 文档目的

这份文档只回答两件事：

1. 测试体系严格化目前已经推进到什么程度。
2. 后续还剩哪些高价值收尾工作。

它强调的是“规范闭环能力”，不是单纯的测试数量。

## 2. 当前结论

截至 2026-04-13，严格化改造已经完成核心批次，当前状态可以概括为：

1. 核心 phase、Git、agent、handoff、resume、delivery、post-condition、exception、config 安全这几条主链路都已有行为测试或反作弊测试覆盖。
2. 关键门禁已经从“源码里写了规则”推进到“运行时 guard + 测试闭环”。
3. 当前测试结果为 `10` 个测试文件、`216/216` 通过。
4. 当前主要剩余工作已经从“补强核心门禁”转向“文档口径统一”和“剩余低价值静态测试继续瘦身”。

## 3. 已完成的关键改造

### 3.1 核心运行时门禁

已形成闭环的重点能力：

1. `main/dev` 受保护分支提交控制
2. 规划文档严格校验与失败阻断
3. review report 的 5 维评分、均分、明确结论硬阈值
4. final acceptance readiness 与发布证据门禁
5. `README` / `final_acceptance_report` / `project_summary_report` 空壳反作弊
6. post-condition 失败后的副作用阻断

### 3.2 行为测试替换静态测试

已完成替换的高价值区域：

1. `m03/m04`：phase/FSM 关键路径（含 FSM 静态字符串测试全部重写为行为测试）
2. `m05`：真实 Git tag、commit、protected branch、副作用验证
3. `m06`：agent 调用合同与 evaluator 一票否决（含结论矛盾/模糊判定）
4. `m11`：checkpoint 恢复、phase skip、sprint 排序
5. `m12`：交付与最终验收文档 gate
6. `m13`：后置条件失败后的无副作用
7. `m14`：结构化交接 anti-cheat

### 3.3 反作弊与审计能力

已经能稳定拦住的典型作弊路径：

1. 文案写“通过”但分数不达标
2. 章节齐全但正文空壳
3. 规划文档校验失败却想继续打 tag
4. 最终验收失败却想继续发布
5. 发布证据不完整却想 merge `dev -> main`
6. 人工介入没有审计提交或提交信息不规范

### 3.4 异常、超时与 metrics

已补强的重点：

1. 异常升级链路有显式 `upgraded` 标记和 metrics 记录
2. `BashTool` 超时路径已有真实触发测试
3. metrics 报告开始做数值级断言，不再只看章节标题
4. `root_cause_archive.json` 已有真实归档校验

### 3.5 配置安全与版本约束

已完成：

1. `loadConfig()` 明文 API key 拒绝测试
2. framework version 不可被本地配置覆盖
3. env-based secrets 与绝对路径解析行为测试
4. 安全命令阻断与 fallback 审计测试

## 4. 当前仍待继续的工作

### 4.1 剩余静态测试继续瘦身

虽然大头已经完成，但仍建议继续检查是否还残留：

1. 只验证源码里包含某个关键词的用例
2. 可以被行为测试替代的配置/常量级断言
3. 低价值重复断言

### 4.2 文档自动化口径

目前已经把主要统计文档改到最新结果，但后续最好进一步做到：

1. 测试执行报告由真实命令输出驱动更新
2. 路线图只记录当前有效结论，不长期保存过时数字
3. README 对外说明当前测试分类与严格性标准

### 4.3 回归池继续累积

后续每修掉一个真实问题，都建议补进回归池，尤其是：

1. Git milestone/tag 命名
2. post-condition 副作用阻断
3. resume 后 phase skip 精度
4. delivery/final acceptance 空壳反作弊

## 5. 推荐的后续顺序

如果继续做最后一轮收尾，建议顺序如下：

1. 再扫一遍测试目录，清理剩余低价值静态断言
2. 把文档统计更新流程再标准化
3. 在 README 或开发文档里固定测试分类标准
4. 继续把新增真实缺陷补进回归测试池

## 6. 当前判断

当前测试体系已经不再是“覆盖很多，但主要靠看字符串”的状态，而是开始具备下面这种特征：

1. 关键规则违反时会在运行时被明确阻断
2. 测试失败信息越来越接近“开发可执行规范”
3. 产物、状态、Git、副作用之间已经开始形成稳定闭环

离最终目标还差的，已经不是“有没有测试”，而是“是否还存在少量没有被闭环约束的边角规则”。这意味着当前阶段的工作重点应从大规模补测试，转向精细化收口和长期维护。
