### 5.3 `GIT_UNIT_005` main 分支保护

| 项 | 内容 |
|---|---|
| 文档位置 | `docs/测试用例文档.md:1033-1040` |
| 测试代码位置 | `harness_meta/test/m05_git_spec.test.ts:74-80` |
| 测试代码预期结果 | 在 `main` 分支直接提交时，`git.commit(...)` 应抛出异常 |
| 测试实际结果 | Promise 正常 resolve，返回提交信息：`feat(project): direct main commit` |
| 失败表现 | `promise resolved ... instead of rejecting` |

对应实现位置：

- `harness_meta/src/git/manager.ts:100-103`
- `harness_meta/src/git/manager.ts:21-57`

当前代码细节：

```ts
async commit(type: string, scope: string, description: string): Promise<string> {
  const message = `${type}(${scope}): ${description}`;
  await this.exec(['git', 'commit', '-m', message]);
  return message;
}
```

代码定位结论：

- `commit()` 没有在提交前读取当前分支，也没有任何 `main` / `dev` 分支保护逻辑。
- `initTargetRepo()` 在 `main` 分支上直接调用 `commit('init', 'project', ...)` 完成初始化提交，这意味着后续实现分支保护时，必须给初始化提交流程保留例外或拆出内部提交接口。

修复提示：

- 在 `commit()` 前增加当前分支判断。
- 明确允许提交的分支集合，例如 `sprint/*`、`fix/*`、`feat/*`、`hotfix/*`。
- 将 `main` 合入和 `dev` 合入收敛到专门的 merge 流程，而不是普通 `commit()`。

- `extractStructuredData('ProductSpec')` 把 `features` 交给 `extractListItems(content, '核心功能')`。

- 当前 `ProductSpecSchema` 只显式校验了 `performance`、`compatibility`、`maintainability`、`security`，没有覆盖文档要求中的“可用性”维度。
- 当前提取逻辑对“用户故事与验收标准”“术语表”“边界范围”也没有真正结构化建模，只是以空数组兜底。
- 这意味着即使把当前失败修掉，模板校验的约束强度仍低于测试文档原始要求。

修复提示：

- 先把“核心功能”列表解析为结构化对象，例如从 `- F-001 login feature` 提取 `id`、`name`，并补充优先级来源。
- 再补齐 `userStories`、`boundaries`、`glossary`、`usability` 等文档要求到 Schema 和提取逻辑。

代码定位结论：

- `extractStructuredData('SprintContract')` 中：
  - `goals` 来源于 `extractListItems(content, '核心目标')`
  - `acceptanceCriteria` 来源于 `extractListItems(content, '验收标准')`

- 先统一 `extractListItems()` 的返回类型，区分“纯字符串列表”和“结构化对象列表”。
